# Deferred event preparation review

Preferred bounded design: all solo event browsing updates the authoritative selected event and its options immediately, while the expensive RaceSimulation/course/render construction happens once at Start. Atlas-only deferral is feasible but adds a Map-close loading boundary and two selection lifecycles. This is a proposal; no runtime source was edited for this review.

## State and boundaries

Keep `currentCourseSeed` as the actually constructed course/network snapshot fence. Introduce a separate pending solo route `{eventId, seed}` initialized for the initial selected event. Never publish the pending seed as the live simulation seed. Reserve fresh expedition seeds on preparing a genuinely new expedition (not every same-event Enter); the existing `nextCourseSeed()` only returns a candidate, and adding the pending candidate immediately to `usedCourseSeeds` prevents repeated deterministic candidates before any course construction. Keep existing ordinal accounting unless deliberately replacing it; do not accidentally increment for both reservation and construction.

Ordinary already-awaiting same-event selection should be a no-op, including preserving custom Expedition laps/mode/difficulty and its pending seed. Resolve canonical event identity (daily/favorite) before this decision, without losing a forced reset path. `restartChampionship()` already mutates selection to the first Cup event: its caller needs explicit forced preparation, or the naive selected-id no-op suppresses the reset's options/preparation. Selecting from a finished race still needs the existing restart/reset cleanup once to enter the garage; repeated browsing in an existing garage does not.

Selection updates `mastery.selectEvent`, selected laps/mode/difficulty, Workshop availability and HUD state. It does not rebuild world geometry. `fixedEventRules()` already derives from selected mastery, and Workshop equip writes the persistent garage loadout independently of the parked simulation. Vehicle class selection continues updating the parked vehicle; Start's constructor consumes the selected class and current actual loadout.

Preview `masteryStartOptions()` and Save course use the pending seed while awaiting in solo. Preview director seed equals that seed: `createRaceDirectorState` returns its supplied seed verbatim, regardless of its internal RNG mix. Do not use stale built-course sector labels in a different pending-course preview; they are presentation-only and can be omitted until Start. Actual-run options after construction use the actual director and sector labels as today.

Solo Start resolves the pending selected route, constructs once with the selected competition profile/options/loadout, and then begins mastery from actual constructed truth. Do not skip construction solely on equal seed: Trial, Flight School and Cup Canyon all share the hero seed but require different field/profile/combat rules. Clear/promote pending only after successful construction. Retry remains exact-current-course rebuild, preserving actual seed and class. Returning from a race to the Expedition garage reserves one new pending expedition; simply closing/reopening Map or Build preserves it. Save before launch, launch and retry must all refer to that same prepared route.

Network start remains governed solely by RoomRaceStart.seed/options/loadouts; pending solo identity must never affect applyRaceStart or the guest seed gate. On leaving a room, explicitly restore valid selected solo options and pending route (preserve a stored solo pending seed if that is the chosen policy; otherwise prepare a fresh Expedition), and defer its world construction. Do not use Open Expedition's catalog placeholder hero seed or silently reuse the last network seed. Capture/review modes retain their explicit forced chaos rebuilding paths.

## Acceptance checks

1. Native Map Arrow selection produces real active transitions and settles by 850 ms without a course rebuild between the first and last sample. Same-event Enter changes neither pending seed, option overrides, simulation object nor construction count. No race starts from Enter on the selected event.
2. Select Expedition -> Save -> close/open Map -> Build equip -> garage -> Start: identical pending/saved/actual seed, actual equipped modifiers, chaos profile and selected options. Exactly one expensive construction at Start. Retry uses that actual seed; return-to-garage allocates one distinct next pending route. Deterministic sequence must remain non-repeating even when browsing away/back without launching.
3. Trial -> School -> Cup Canyon (same seed): preview selected rules are immediate; Start produces respectively time-trial/training/clean-race profiles, correct field size/laps/stock loadout/combat limits. Cup Next carries standings; explicit Restart Cup resets standings/options and prepares first round even though RaceMastery has already selected it.
4. Saved favorite and UTC daily previews use the correct resolved identity, including PB/ghost and courseSaved matching. A pending different seed never borrows a stale built-course director identity or sector labels.
5. Host/guest actual start and rematch retain identical authoritative seed, profile, roster and loadouts; guest old-seed snapshots remain rejected. Leaving a room restores a valid solo preparation without a hidden stale network seed. Existing live game snapshots remain truthful about what course is actually built.
6. Test the pending lifecycle as behavior (a small pure preparation helper is suitable), not by regex checks that merely mirror GameApp source. Native capture is still necessary for the main-thread hitch. Existing courseSeedLifecycle tests cover RaceSimulation reset/generation, not this pending lifecycle.
